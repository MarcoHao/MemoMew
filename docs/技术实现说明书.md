# MemoMew 技术实现说明书

## 一、技术架构

### 1.1 整体架构

MemoMew 采用 **Electron + React + TypeScript** 技术栈，前后端分离的桌面应用架构：

```
Electron Main Process (Node.js)
  ├── 系统层: clipboard, globalShortcut, Tray
  └── 数据层: better-sqlite3 (SQLite)

Electron Renderer Process (Chromium)
  ├── UI层: React 19 + Tailwind CSS
  ├── 可视化: D3.js (知识图谱)
  ├── 语音: Web Speech API
  └── AI: Kimi API (RESTful HTTP)
```

### 1.2 通信机制

主进程与渲染进程通过 **Electron IPC** 通信：
- `contextIsolation: true` 启用上下文隔离
- `preload.ts` 作为安全桥梁暴露API
- 数据库操作在渲染进程中通过内存数据库实现（开发环境），生产环境通过IPC调用主进程SQLite

## 二、核心模块实现

### 2.1 宠物动画系统 (`PetAvatar.tsx`)

**技术方案**: HTML5 Canvas 2D 逐帧动画

**状态机设计**:
```typescript
type PetState = 'idle' | 'listen' | 'think' | 'speak' | 'happy';
```

**动画参数**:
- `idle`: 正弦波驱动身体浮动 + 尾巴摇摆
- `listen`: 耳朵旋转角度增大，模拟警觉状态
- `think`: 眨眼频率增加，身体轻微抖动
- `speak`: 嘴巴张开闭合 + 身体弹跳
- `happy`: 腮红效果 + 快速弹跳 + 大幅度摇尾

**渲染管线**:
1. `requestAnimationFrame` 驱动60fps渲染循环
2. Canvas 2D API 绘制路径和填充
3. 保存/恢复上下文实现层级变换

### 2.2 知识图谱系统 (`GraphView.tsx`)

**技术方案**: D3.js v7 力导向图 (Force Simulation)

**数据流**:
```
笔记保存 → Kimi API抽取实体关系 → 存入SQLite
                             ↓
                    读取 entities + relations 表
                             ↓
                    D3 forceSimulation 渲染
```

**核心配置**:
```javascript
simulation = d3.forceSimulation(nodes)
  .force('link', d3.forceLink(links).distance(100))
  .force('charge', d3.forceManyBody().strength(-300))
  .force('center', d3.forceCenter(width/2, height/2))
  .force('collision', d3.forceCollide().radius(30));
```

**交互特性**:
- 拖拽节点: `d3.drag` 绑定拖动事件
- 点击查看详情: 节点 `click` 事件显示右侧面板
- 颜色编码: d3.scaleOrdinal 按实体类型分配颜色

### 2.3 AI知识引擎 (`kimi.ts`)

**API封装**: 基于 Fetch API 的 Kimi RESTful 客户端

**核心Prompt设计**:

1. **笔记摘要**:
```
请为以下笔记内容生成一句话摘要和3-5个标签。
以JSON格式返回：{"summary": "...", "tags": ["..."]}
```

2. **实体抽取** (知识图谱构建):
```
请从以下文本中抽取知识图谱的实体和关系。
实体类型：人物、组织、地点、概念、技术、事件等。
JSON格式：{"entities": [...], "relations": [...]}
```

3. **问答RAG**:
```
基于以下知识库内容回答问题。
如果知识库中没有相关信息，请坦诚告知。
```

**错误处理策略**:
- API Key未设置 → 提示用户配置
- 网络超时 → 降级使用本地搜索
- API调用失败 → 仍保存笔记，不阻塞用户操作

### 2.4 语音系统 (`speech.ts`)

**技术方案**: Web Speech API (浏览器内置)

**TTS (语音合成)**:
```typescript
const utterance = new SpeechSynthesisUtterance(text);
utterance.lang = 'zh-CN';
utterance.pitch = 1.1; // 调高 pitch 使声音更可爱
```

**STT (语音识别)**:
```typescript
const recognition = new webkitSpeechRecognition();
recognition.lang = 'zh-CN';
recognition.continuous = false;
recognition.interimResults = true; // 实时返回中间结果
```

**优势**:
- 完全免费，无需API Key
- 支持中文，识别准确率良好
- 浏览器原生支持，无需额外依赖

### 2.5 数据存储 (`db.ts` / `db/index.ts`)

**双模式存储**:

| 环境 | 存储方案 | 说明 |
|------|---------|------|
| 开发 | 内存对象 | 便于快速迭代测试 |
| 生产 | better-sqlite3 | 持久化本地存储 |

**SQLite Schema**:
```sql
CREATE TABLE notes (
  id INTEGER PRIMARY KEY,
  title TEXT, content TEXT,
  summary TEXT, tags TEXT,
  created_at, updated_at
);

CREATE TABLE entities (
  id INTEGER PRIMARY KEY,
  name TEXT UNIQUE, type TEXT,
  description TEXT, note_ids TEXT
);

CREATE TABLE relations (
  id INTEGER PRIMARY KEY,
  source_entity TEXT, target_entity TEXT,
  relation_type TEXT, note_ids TEXT
);
```

## 三、关键设计决策

### 3.1 为什么不用完整的Nano-GraphRAG？

Nano-GraphRAG是Python库，引入会增加：
- Python运行时依赖（打包体积+复杂度）
- 跨语言调用开销
- 部署复杂度

**替代方案**: 简化版知识图谱
- 用Kimi API做实体关系抽取
- 自行存储到SQLite
- D3.js做可视化

**权衡**: 牺牲部分自动化能力，换取开发速度和打包简洁性。

### 3.2 为什么用Web Speech API而不是Kimi TTS？

- Kimi目前**不公开TTS API**（Kimi-Audio有TTS但不对外开放）
- Web Speech API完全免费，浏览器内置
- 无需额外网络请求，延迟更低
- 支持中文语音合成和识别

### 3.3 为什么用内存数据库作为开发fallback？

better-sqlite3在纯Vite开发服务器环境中需要Electron主进程支持。在开发阶段使用内存对象，可以：
- 脱离Electron环境快速迭代UI
- 不需要配置native模块加载
- 数据重置方便（刷新页面即清空）

## 四、性能优化

### 4.1 渲染优化
- Canvas宠物动画使用 `requestAnimationFrame`，避免重绘
- 知识图谱使用D3的力模拟，仅更新transform属性
- React组件使用useCallback/useMemo减少重渲染

### 4.2 数据优化
- SQLite启用WAL模式，提升并发性能
- 笔记列表仅加载标题和摘要，不加载完整内容
- 聊天上下文限制最近10条笔记

### 4.3 打包优化
- electron-builder配置排除不必要的node_modules
- 最终打包体积目标: < 150MB
